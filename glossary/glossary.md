
# 用語集

## CommonMark

**読み:** こもんまーく  
**更新:** 2026-06-06  

[Markdown](#markdown)の曖昧さを減らすために作られた、標準化されたMarkdownの仕様。

構文セットとしてはやや少なく、表や脚注などの構文は準備されていない。ドキュメントサイト生成ツールはCommomMarkを基準にサポートしていることが多く、追加で[GFM](#github-flavored-markdown)を意識した構文拡張が行われていたり、プラグインなどで拡張できる仕組みが提供されている。

### 参考

* [CommonMark](https://commonmark.org)

## GitHub Flavored Markdown

**読み:** ぎっとはぶ ふれーばーど まーくだうん  
**別名:** GFM  
**更新:** 2026-06-06  

GitHubが拡張したGitHub上で利用できるMarkdown構文。標準のMarkdownよりも構文が拡張されており、表やタスクリスト、脚注やAlerts（callouts/admonitions）などが利用できる。様々なサービスが参考としているためMarkdownというとGFMがイメージされるところがあるが、標準仕様からはだいぶ拡張されているため、一位の構文がサポートされていなかったり、記述方法が異なる場合がある。

GitHubのIssueなどで利用でき、GtHub上で綺麗にレンダリングされるため、GitHubを中心に活動する場合はGFMを利用して記述するとよい。[Mermaid][mermaid]もサポートされており、テキストからブロック図やフローチャートを記述することもできるようになっている。

ただし、ドキュメントサイト生成ツールを利用する場合、サポートされている構文の差に注意が必要である。例えば[Astro][astro]ではGFMのAlerts構文はサポートされていない。ツールの拡張機能なので利用できる構文をそろえるか、最終出力を意識して仕様する構文に注意するかの対応が必要となる。

### 参考

* [Basic writing and formatting syntax](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)
* [GitHub Flavored Markdown Spec](https://github.github.com/gfm/)

## Markdown

**読み:** まーくだうん  
**更新:** 2026-06-06  

Markdownはプレーンテキストのフォーマットで、簡単に読み書きできるプレーンテキストからHTMLに変換するための仕組みとして構築もの。プレーンテキストの整形構文と変換ツールからなる。

オリジナルのMarkdownは一通りの構文は揃っているものの、表やFenced code blockなど、一部の構文は準備されていない。様々なサービスやソフトウェアで利用できるが、それぞれで利用できる構文には微妙な違いがあるため、ターゲットとするソフトウェアに合わせた書き方が必要となる。

仕様としてはやや曖昧で、その曖昧さを標準化するために[CommonMark](#commonmark)が作成された。

### 参考

* [Markdown](https://daringfireball.net/projects/markdown/)

## SPLADE（Sparse Lexical and Expansion Model）

**読み:** すぷれいど  
**更新:** 2026-06-12  

完全一致だけに頼らず、関連語も含めた“賢いキーワード検索”をニューラルモデルで実現する手法。テキストをトークン化し、関連する語彙を拡張する。たとえば「リモートワーク」という検索クエリに対して、「遠隔」「勤務」「テレワーク」といった関連語にもスコアを付与してマッチさせることができる。

## 指数バックオフ

**読み:** しすうばっくおふ  
**別名:** exponential backoff  
**更新:** 2026-06-12  

リトライの間隔を指数的に増やす方法。（例：100ms→200ms→400ms→800ms）。失敗が続くほど間隔が広がるため、障害中のサービスへの負荷を徐々に軽減できる。実運用ではジッター（jitter）と呼ばれるランダムな揺らぎを加えて、複数クライアントからのリトライのタイミングも分散させる。

## テスト設計

**読み:** てすとせっけい  
**更新:** 2026-06-06  

テスト設計は「どのようにテストするか？」に答える活動。[テスト分析](#テスト分析)の結果得られたテスト条件からテストケースを作成する。テスト技法が用いられる。

テスト設計にはテスト環境の設計やインフラ、ツールなどの識別も必要となる。

テスト設計の成果物として以下のものが挙げられる。

* 優先順位付きのテストケース
* テストチャーター
* カバレッジアイテム
* テストデータ要件とテスト環境要件

### 参考

* [JSTQB FL シラバス][jstqb-fl]

## テスト分析

**読み:** てすとぶんせき  
**更新:** 2026-06-06  

テストベースを分析して、「何をテストするか？」という問いに答える活動。

テスト可能な機能を識別し、テスト条件を定義して優先度をつける。リスクの列挙とリスク分析も行う。この際テスト技法が使用される。

テスト分析の成果物として以下のものが挙げられる。

* 優先順位付きのテスト条件
    * 受け入れ基準
* リスクの列挙と分析
* テストベースへの指摘

### 参考

* [JSTQB FL シラバス][jstqb-fl]

## テストベース

**読み:** てすとべーす  
**更新:** 2026-06-06  

テスト分析・テスト設計に必要な情報全般のこと。

要件定義書や仕様書、GitHubのIssueや機能説明用のプレゼンテーションファイルなどが該当する。開発チームによって情報のまとめ方や出し方が異なるため、開発チームごとに重視する情報は異なる。

ソフトウェアテストの活動は開発者が行う変更が開発者の意図通りに実施されているかを確認・保証することが中心となるため、仕様書やIssueが中心となりやすい。ただし、ユーザーの立場に立って機能や変更が適切なものとなっているかといった、より広い視野での品質評価を行う場合は、ソフトウェアが提供される業界やユーザー、法律や規格などの幅広い情報や知識が必要となる。

### 参考

* ソフトウェアテスト徹底指南書

## テストレベル

**読み:** てすとれべる  
**更新:** 2026-06-06  

あるテストが持つ責任範囲や目的をレベル分けしたものをテストレベルと呼ぶ。

* ユニットテスト（コンポーネントテスト）
* 統合テスト（コンポーネント統合テスト/結合テスト）
* システムテスト
* システム統合テスト
* 受け入れテスト
